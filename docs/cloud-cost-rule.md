# Cloud cost discipline

This is the repository copy of the owner-wide Codex rule approved on 25 November 2026. Use it for GitHub Actions, other remote execution and manual releases, including the first billable build, upload or cloud command.

## Owner-wide cloud cost rule

1. **Get approval before increasing cost exposure.** Local development, isolated emulators, verified no-cost reads, and routine releases within the approved operating limits need no separate cost approval. Before creating or enabling paid resources, changing billing or credit routing, or adding recurring or burst usage outside those limits, obtain explicit owner approval. Apply the same gate when incremental exposure is unknown. Every spending approval request must present a forecast to the owner before approval is sought. Include the estimated one-time cost, normal monthly incremental gross cost, credible high-usage monthly gross cost, underlying usage and pricing assumptions, verified credit coverage (account, eligible usage, amount and expiry), estimated net out-of-pocket cost, and uncertainty. Clearly mark unverified coverage and exclude it from the net estimate. Never present unknown cost as zero or ask for blind approval. If evidence cannot support a defensible forecast or range, keep the work unapproved and resolve the missing inputs. Approval must identify the project and billing account, the approved spend or usage limit, and the end date for trials. A billing-enabled project, free allowance without verified headroom, or available credits grants no spending authority.

2. **Make idle cheap and failure bounded.** Prefer work triggered by user demand or real events. Share and scope listeners, release them when idle, and avoid eager full reads and no-op writes. Fixed polling, keepalives, warm instances and long-lived cloud requests require a measured need and an explicit bound within the approved limits. Set end-to-end deadlines, stop abandoned work, and bound retries and reconnects with backoff, jitter and deduplication. Retry only failures that can recover. Keep authorization, revocation, lease safety, data integrity and required user outcomes intact.

3. **Size and bound the deployed workload.** For a cost-changing release, record the normal and credible high-usage estimates, including quiet traffic, long requests, failure bursts, storage and transfer where relevant. Set and verify the billing mode, instance limits, concurrency, CPU, memory, timeouts and admission limits that control that exposure. Default to scale-to-zero where supported and compatible with the service. Deploy only affected targets. Bound the retention of images, builds and other deploy artifacts, and verify that live and rollback versions are protected before any cleanup.

4. **Verify cost as part of the release.** Before the first billable action, record the baseline, approved limits, billing source, review time and safe rollback or containment action in the existing release record. After rollout, verify the exact deployed revision and settings, the real authorized workflow, and the relevant idle, long-request and retry behavior. Reconcile the first complete comparable billing window once provider data arrives. Record incurred gross cost, applied credits and net cost separately from forecasts, and confirm credit scope and expiration before relying on credits. Keep cost verification open while data is missing. Freeze expansion on an unexplained breach and follow the approved containment or rollback. Budget alerts are signals. Any automatic service interruption requires explicit approval.

## Existing release checks

Use the current release checklist, workflow summary or release evidence for the forecast and verification. Existing deployment scope checks, billing prerequisites and runtime readback provide inputs to the rule. Record owner approval separately when required. Use the provider's existing billing view or an authorized export for incurred cost. Follow the project's additional cost and data controls, including the [GTOP and GT Papers Firestore Efficiency Standard](https://github.com/Wolfrine/gtop-app/blob/main/docs/engineering/firestore-efficiency.md).
