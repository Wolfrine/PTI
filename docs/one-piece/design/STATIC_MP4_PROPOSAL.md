## Delivery and track requirements

Retain `{episodeId,mediaUrl,subtitleUrl,contentType,durationSeconds,expiresAt}`. The MP4 response uses HTTP `Content-Type: video/mp4`, accurate length, byte-range support and consistent 200/206/416 handling, including HEAD and late seeks. Verify metadata placement and startup from actual bytes; do not presume that an MP4 extension makes a file ready for progressive playback. API routes, cookies, arbitrary files, redirects and engine credentials remain inaccessible to the viewer.

Prepare the inspected selected Japanese audio into the delivered file, with browser-compatible video/audio established by the pilot. Keep audio selection in the existing server-backed track UI; native browser multi-audio track support is not required or assumed. Report the actual effective selected language. A later English selection, when available, rebuilds the selected delivery and preserves position/paused intent using the existing path.

Full English dialogue remains an external `text/vtt; charset=utf-8` track with `kind=subtitles`, `srclang=en`, and the existing default/showing versus off setting. Do not rely on embedded MP4 subtitles or a songs/signs track. Native media and VTT use `crossOrigin=anonymous`, valid HTTPS on local viewing, permitted PTI/development origins, no cookies and no service-worker media caching. Both must remain accessible through authorized range/track requests until renewal or explicit revocation. Cast has a separate admission and receiver validation path; native browser success does not certify it.

For source replacement/renewal: invalidate older play attempts, pause, destroy any HLS instance, detach old metadata/track continuations or make them generation-inert, remove old sources/tracks, and load the new source. Apply the saved finite/clamped position after new metadata and preserve paused intent. Destroy/sign-out must abort native loading via source removal/load and make stale play/track callbacks inert. Existing loadedmetadata/track callbacks already check source generation; tests must verify no old-source error or metadata callback corrupts replacement state. Change lifecycle code only if a test or actual reproduction exposes a gap.

## Conditional regression plan

Use the existing Node tests and EventTarget video stub; no new framework. Add MIME-routing tests proving MP4 never constructs hls.js, recognized HLS retains its current branch, and unknown MIME fails explicitly. Update test deliveries to declare MIME rather than depending on the current stub always claiming native HLS support. Verify English track URL/language/default/showing-off behavior, metadata-resume clamping and one normalized autoplay attempt. Exercise HLS→MP4, MP4→HLS and MP4→MP4 renewal/replacement with older pending play/metadata/track completions, paused renewal, destroy and an intentional rapid play/pause rejection. Keep UID race, native/page keyboard and secret-free diagnostics regressions. These prove routing/state only, not real decode, seeking or subtitles.

Backend tests remain the parent's lane: accurate MIME/length/ranges, exact resource/episode allowlist, no engine secret leakage, old-epoch/revoked/expired denial and selected audio/full-English provenance. Do not weaken tickets for a static-file path.

## Matched browser experiment before choosing

Compare current HLS and fully prepared MP4 for the **same source episode and effective audio/subtitle selections**, through the scoped production media adapter and the same LocalPlayer control path in a development-only harness. Record any encode or audio change: if MP4 is encoded while HLS copies video, that is a delivery-plus-encode comparison and cannot isolate the container. Where possible compare matched encoded tracks, then separately test forced-compatible versus copy variants. Do not run concurrent encoders or interrupt the TV lane.

For each path use a fresh instance/tab, record browser version/mode/actual tracks/duration, and run the captured sequence: metadata/resume at 600 seconds while paused → native ArrowLeft (browser step) → page ArrowLeft (10 seconds) → page Space play/pause → native Space play/pause → five page ArrowRight presses. Use deterministic press/release and log positions, paused/seeking/readyState, native error code and sanitized HLS type/details before destructive error handling. Also test single early/late forward/backward seeks, play after seeking, rapid repeated seeks, pause/resume, caption off/on with visible English after seeks, delivery renewal preserving pause, and 1000→1001. Repeat with both source collections; the second collection's different video/audio source is a separate compatibility case.

Measure request-to-first-presented-frame with required captions ready, warm seek-to-render recovery, transferred bytes and request status/range evidence. A `seeked` event or `readyState=4` alone does not prove a displayed frame, audible Japanese or synchronized English. Compare repeat warm runs against the retained five-second target; separate one-time preparation cost. Retain actual screenshots/observations and sanitized diagnostics without capability URLs. A run that avoids code 3 is encouraging but cannot establish full-episode, Android, HDMI, Cast or three-session reliability. No performance or decoder-fix claim is made before this experiment.
