## Chat lifecycle (owner instruction, 2026-11-02)

Use an explicit stable `module_key` when the request establishes the functional module; never route by fuzzy titles. The owner-scoped `modules/{affinity-id}` registry is keyed by canonical physical project path, checkout resource and module key, separately from task/work identity. It stores only the current native parent pointer and revision/task provenance. Admission reserves a module even before its first native thread exists, and active modules reject additional parent tasks with the owning ID. Task and registry/reservation updates are transactional. Worker native/module locks and unfinished-turn checks also apply.

Same outcome uses `continue_task`. A different related outcome uses a NEW task/work key in its current authorized mode, selecting the same module parent and refreshing current instructions/permissions before inference. Caller `sourceThreadId`, immutable router `selectedThreadId` and learned `threadId` have separate meanings. Missing legacy source provenance permits only a provably identical work-key retry; otherwise explicitly continue or choose a new outcome key. No module key preserves compatibility and makes no historical guess. Exact source adoption uses `resume_codex_thread` with the selected native ID and module; no historical migration is automatic.

Idle `notLoaded` threads resume. Module selection checks metadata only, including archived state; confirmed missing/archived/incompatible automatically selected parents may rotate with a recorded predecessor/reason. Explicit source and same-outcome threads never silently change; active threads and uncertain protocol errors stop. Context bloat uses explicit `chat_policy:rotate`, a reason and a compact supplied handoff of project evidence. There is no arbitrary context-age/turn/token cap, archive, delete or transcript copying. Registry revisions prevent old reports/continuations from repointing a rotated module. See `decisions/2026-11-02-chat-lifecycle.md`.

## Caller-selected result waits (owner instruction, 2026-11-03)

ChatGPT chooses each hosted `get_task.wait_seconds` from expected remaining work, recent progress and desired responsiveness. Longer supported waits fit quiet long work; shorter waits fit imminent results or human interaction. Twenty seconds is an omitted-argument compatibility fallback, not a fixed polling schedule. Respect actual connector metadata and client timeouts; verify a larger wait through that connection. Progress and human decisions return early; request timeout never limits task execution. A saved connector schema can remain stale after server/plugin publication and must be refreshed separately.

## Effectiveness loop

Owner instruction, 2026-11-02: use Firestore listeners for PC work notifications and hosted ChatGPT result waits. Keep health/lease maintenance separate, avoid quiet queue queries and repeated unchanged writes, and include sanitized cumulative transport counters in the review. Request counters are not measured Firestore billing. The 0.4.3 transport decision and its regression/installed evidence are in `decisions/2026-11-02-listener-transport.md`.

The daily 10:30 Asia/Kolkata heartbeat runs the deterministic seven-day review documented in README. The review uses owner-scoped bridge metadata and bounded per-generation local telemetry. It records timing, human-wait time, command/tool failures, child activity and selected settings, with latest-response token observations when available. It omits prompts, final answers, command text/output, credentials and unrelated chats. It excludes declared acceptance probes from ordinary-work metrics. Older missing fields remain unknown.

`record_task_outcome(task_id, generation, outcome)` records only an explicit human `accepted`, `needs_rework` or `abandoned` verdict for that completed generation. Silence, successful execution, passing tests and a deployment are not acceptance. Owner-scoped outcome history is bounded and generation-bound. The private worker review endpoint returns sanitized metadata only. Account-wide allowance is headroom, never task attribution.

The collector requests exact remote task IDs mapped to local generations in its review window, in transport batches of 100 with no total lookup cap. It never substitutes the most-recent-100 listing for that scope. Missing records, unmapped local tasks and absent generation verdicts remain unknown; fetching all requested jobs does not recover unrecorded history. See `decisions/2026-11-05-scoped-review-feedback.md`.

The report separates ordinary work, acceptance probes, missing coverage and observational comparisons. Initially there is no basis to claim that this harness reduces time/tokens or improves owner outcomes. Admission rejection/retry counts and full-generation token cost are not yet measured. A review with sparse or unchanged data records no change.
