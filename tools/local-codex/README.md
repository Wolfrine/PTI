# Local Codex from normal ChatGPT chats

The private Local Codex plugin calls `/local-codex/mcp` on PTI's existing Cloud Run service. Eighteen work/history/outcome/capability/QA tools serve the owner through the existing authenticated connection. The discussion stays in the normal ChatGPT conversation, including on web/mobile clients that support the connected plugin.

The worker launches the installed Codex CLI's app-server using the Windows user's **ChatGPT subscription sign-in**. It rejects API-key authentication and removes model API credential/endpoint overrides from child environments. Codex credentials never leave the PC. PTI Firebase OAuth authorizes the relay; a separate current-user DPAPI credential authorizes the worker. This is not an OpenAI inference API integration.

## Operation

Source: `tools/local-codex`; installation: `F:\Workspace\Support\LocalCodexBridge`. Existing config and task history are preserved. `config.json` contains the F-drive project allowlist. Omit `codexPath` to select the newest installed desktop runtime. Platform-managed Codex binaries, sign-in and session state retain their required Windows locations.

Version 0.3.3 requires `firebaseAuthApiKey` in the installed configuration. Use the public `native-firebase-auth` artifact from the existing PTI shared MCP workflow. It provisions/reuses only `pti-native-firebase-auth`, restricted to `identitytoolkit.googleapis.com` and `securetoken.googleapis.com`, and verifies native refresh without a Referer. The Firebase project and owner authorization stay the same; existing encrypted refresh tokens can be reused. Browser/Picker keys and project IAM are not modified. Do not use a browser-only key or fabricate a browser Referer for a native worker.

The owner's current model preference is `model: "gpt-6.1-sol"`, `reasoningEffort: "xhigh"`. Every new task and continuation checks the signed-in model catalog, passes the pair explicitly on thread start/resume and turn start, and verifies the runtime's confirmation before inference. If the pair is missing, unsupported, replaced, or advertises an upgrade, the task stops and asks the owner to choose. There is no automatic lower-model fallback. `bridge_status` reports the configured pair; task results report the confirmed pair. This applies to work launched by this bridge, not independent native chats.

Build with `npm ci --ignore-scripts`, `npm run build`, then `npm test` on Windows. Run `install.ps1 -NoSchedule`, then the installed `run.ps1 -Command setup` to pair through Google. Run `install.ps1` to register **PTI Local Codex Relay**. Its `wscript.exe` launcher hides PowerShell and descendants from creation; scheduler overlap protection and a worker lock prevent concurrent instances. It starts at login and retries every minute, while the user is signed in. Check installed `data/status.json` and authenticated `bridge_status` for live availability. Stop the named scheduled task to stop accepting work; active child work also stops if connectivity is lost for 45 seconds. Do not delete task history when upgrading.

The PC must be awake, online and signed into ChatGPT. Submission requires a heartbeat younger than 60 seconds. Unclaimed jobs expire after two minutes; claimed jobs have a renewable 90-second lease. A lost lease reports interruption and cannot renew later. Resume explicitly with `continue_task`; it retains project/mode. Reuse an exact request key on retries. Cancellation cannot undo completed edits.

For explicitly authorized remote setup, `node dist/pair-existing.mjs --reuse-pti-signin` can reuse this Windows user's already encrypted PTI usage-monitor owner sign-in. It verifies the Firebase account/project and current Codex ChatGPT auth, refreshes through Firebase, then protects a separate credential under the relay's own DPAPI entropy. It does not change the monitor's files. This option shares the existing Firebase login's revocation lifecycle; use Google pairing for an independent login. No Codex model credential is copied.

## Authorization and evidence

### Interactive QA broker (host 0.4.5, worker 0.4.8)

`get_capabilities` and `bridge_status.capabilities` distinguish Desktop/browser handoff, unverified speaker playback, and unsupported audio capture/analysis. `request_interactive_qa` persists an owner-scoped request for an exact project/revision/URL/build/objectives/device. `get_interactive_qa`, `list_interactive_qa`, and `update_interactive_qa` expose handoff, external-run reservation, receipt and complete/fail/expire/release lifecycle. No verified programmatic Desktop-session provider is supported; no browser is launched. Old workers remain compatible with unknown preflight telemetry. An official Desktop operator can report observations and captured artifact references, with explicit attestation and unverified provenance. A report is not independent QA or owner acceptance. See the [broker contract and operator steps](decisions/2026-11-07-interactive-qa-broker.md).

Hosted support must deploy before worker 0.4.8 activation. Install only while all existing claims are idle; never restart the delivering task or Ragnarok work. Source/build version, hosted deployment, installed worker and plugin publication are separate states.

### Browser context preflight (runtime 0.4.7)

The bridge starts an independent `codex app-server --stdio`. Its Full Access setting, subscription sign-in and Firestore connectivity do not establish browser control. Before inference, each worker checks only whether its own child environment has both app-session browser prerequisites. Missing or incomplete context is `unavailable`; both present is still `unverified`, never ready or accepted. No pipe/identity values are retained or returned. The sanitized result appears in local task `browserContext` and the internal worker `bridge_status`; this does not add fields to the hosted status protocol.

New threads and every resume/continuation receive current trusted browser instructions before the turn. With unavailable context, skip browser initialization and host retries, report any required browser step promptly, and continue independently possible coding/CLI work. With unverified context, only an available official tool's normal entry point can establish access; a host or policy failure ends that browser step without retrying. There is no prompt-keyword rejection, automatic app-owned session routing, identity/pipe recovery, URL-policy bypass or raw Playwright/CDP fallback.

For browser work, open a chat in the ChatGPT desktop app on this PC and invoke `@Chrome`. From mobile, select this connected host through Codex (Remote in older apps), with Computer Use enabled and the Chrome extension installed on the host. Keep Windows awake and unlocked. Follow the official [browser guidance](https://learn.chatgpt.com/docs/browser) and [remote connection setup](https://learn.chatgpt.com/docs/remote-connections). This entry point does not repair the separately reported native Windows URL-policy failure, and actual browser control still needs verification there.

Activate 0.4.7 with the existing `install.ps1` only after tests/build and when **all** relay claims are idle. The active worker keeps its loaded release/instructions; source delivery alone does not activate this preflight. See the [bounded repair decision](decisions/2026-11-06-browser-context.md).

### Module chat lifecycle (0.4.4)

`module_key` names an explicit stable functional module, such as `local-codex`. Related outcomes use the same module key with different `work_key` values: they get NEW task/authorization records and reuse the module's idle native parent in the same physical project/checkout. Same outcome uses `continue_task`. `resume_codex_thread` can explicitly adopt a selected existing parent into a module. Caller source identity is stored separately from router selection and learned native identity; work-key retries no longer mistake a learned thread for a different caller source.

The existing owner-only server namespace contains durable `modules/{hash}` pointers. Task admission, module selection and reservations share one Firestore transaction. Active modules, native threads and conflicting workspaces identify their owner and reject competing work; prefer native subagents coordinated by that parent for independent lanes. Mode changes create a new task and refresh permissions/instructions on the reused thread. Physical aliases share affinity; other projects/checkouts/modules do not. An omitted module key remains compatible and never guesses from titles.

Stored `notLoaded` chats can resume. Native metadata and unfinished-turn checks protect selection. An automatically selected missing/deleted, archived or incompatible thread can be replaced with an audited reason; an explicit source or task continuation cannot silently switch. Transient or ambiguous failures stop. Explicit `chat_policy:rotate` requires `module_key`, `rotation_reason` (`context-bloat`, `incompatible`, `invalid`) and a compact `handoff` of project facts/evidence; it does not archive/delete the former chat or copy a transcript. No context-size/age/count threshold is imposed. Previous tasks and their authorizations remain intact.

The MCP schema and plugin skill expose these optional fields. Older workers reject module routing before queueing; upgrade the worker to 0.4.4 before using it. Existing tasks without module metadata keep their existing behavior. See [lifecycle decision](decisions/2026-11-02-chat-lifecycle.md).

### Terminal worker PID reuse (runtime 0.4.5)

A terminal task can retain a PID that Windows later assigns to an unrelated process. Continuation checks the process birth time before treating it as the previous worker still exiting. A birth strictly after the terminal timestamp proves reuse; unknown timing retains the existing wait. No unrelated process is stopped. See [the evidence and regression decision](decisions/2026-11-03-recycled-worker-pid.md).

### Listener transport (0.4.3)

The PC holds one Firebase `onSnapshot` subscription on `_ptiLocalServices/local-codex/owners/{owner}/signals/dispatch`. The owner can get only this exact marker; collection queries, sibling documents, jobs and client writes remain denied. It contains only a version, random revision and timestamp. The existing encrypted Firebase session supplies a public `FirebaseServerApp` user context; no Admin credential or new sign-in is installed. The session is replaced before token expiry, with SDK reconnect handling and fresh discovery on each server reconnection.

Enqueue/continuation, cancellation and a new human answer change the marker atomically with their transaction. Heartbeats, leases and progress never change it. The worker calls authenticated `/worker/sync` with `dispatch:true` after a notification; dispatch reads each ten-job page once and drains full pages. Connected idle workers now receive a 40-second maintenance delay; active claims and disconnected listeners retain 30 seconds. Notifications still wake immediately. Maintenance uses `dispatch:false`: no queue query, one root plus one read per active claim in a single transaction, with due-only lease/root writes. The online cutoff remains 60 seconds; network latency consumes the nominal freshness margin. Existing 0.4.3/0.4.4 relays already honor the server-provided delay, so this server correction needs no relay restart. Old workers keep their compatible `/poll` endpoint until upgraded. Listener outages suspend new admission while existing leases can renew.

Local task-file changes wake progress reporting; unchanged progress and telemetry-only changes are suppressed. Final telemetry is retained, failed reports retry and claims keep generation/lease identity. ChatGPT's `get_task` also uses its initial listener snapshot without an extra document read. `data/relay-state.json`, `data/status.json` and the daily review expose cumulative request/event counters, not provider billing. No measured cost saving is claimed from these counters alone. SDK listeners remain metered for initial snapshots, updates and reconnects. See [Firebase user-context authentication](https://firebase.google.com/docs/web/ssr-apps) and [listener billing](https://firebase.google.com/docs/firestore/pricing#listening_to_query_results).

### No arbitrary execution caps (0.4.2)

The owner explicitly withdrew the bridge-generated three-parent, two-child, single-layer and 30-minute ceilings. `maxConcurrentTasks`, `maxSubagentsPerTask` and `maxTaskMinutes` default to `null`, meaning no bridge cap. This is not a large replacement number. Admission, heartbeat schemas and durable recovery accept more than four claims; child observation has no 16-agent cutoff. Numeric settings remain available only for an explicit owner choice. Ask before introducing a new restriction.

Native Codex still chooses its own subagent concurrency when its optional setting is omitted; the bridge neither invents a native unlimited sentinel nor claims platform limits disappear. Native descendants remain subject to the exact Sol/xhigh contract and current task ownership. Real workspace/shared Git and native-thread conflicts still require coordination. Existing active workers keep their loaded policy until their next explicit continuation; release activation does not cancel or restart them.

### Trusted edit permissions (0.4.1)

The owner explicitly requires parity with the trusted desktop's Full Access setting. Edit tasks use `danger-full-access` with approval `never`; inspect tasks remain `read-only` with approval `never`. Before inference the worker verifies the returned sandbox, approval policy, model and effort. Permission mismatches fail before a model turn. Full Access permits authorized filesystem and network operations, including Git delivery and named service paths; the selected project, current user request, applicable instructions and ownership still define scope. It is not filesystem isolation or permission for unrelated actions.

On historical-thread resumption, the worker appends fresh trusted current-mode instructions using `thread/inject_items` after validating the session. A runtime may retain its initial developer message despite accepting `thread/resume.developerInstructions`; re-supplying that field alone did not remove the old inspect restriction. Failed instruction refresh stops before inference. `continue_task` still cannot change mode/project; explicitly authorized inspect-to-edit resumption creates a separate bridge job on the selected idle native thread. Existing running tasks keep their original policy until explicitly continued through the upgraded worker.

### Thread continuity and organization (0.3.0)

Use `continue_task` for the same outcome/project/mode. `list_tasks` recovers recent IDs by project/title/work key. `start_task` accepts a short `title` and stable `work_key`; another submission for that project/mode/work key returns the existing task instead of creating a thread. `reused: true` does not submit the new prompt: inspect the task, then explicitly continue it. Changed arguments on an exact request-key retry remain rejected. This is explicit work identity, not an inferred ChatGPT conversation ID; clients retain the work key. Task lookup filters the most recent 100 records.

## Daily effectiveness review (0.4.0)

Run `node tools/local-codex/src/review-usage.mjs --days 7 --sync` from the PTI repository, or `node F:/Workspace/Support/LocalCodexBridge/releases/<active-release>/review-usage.mjs --days 7 --sync` using the installed release recorded by active.json. The native heartbeat is scheduled for 10:30 Asia/Kolkata daily. It needs this PC and the Codex application available; verify the saved automation instead of treating this document as a scheduler.

The command aggregates local per-generation timing, tool failures, child selection coverage and latest-response token observations. It syncs only sanitized owner-scoped metadata/feedback through the existing Firebase credential. Reports omit prompts/finals/tool output and default to `F:/Workspace/Support/LocalCodexBridge/harness/reviews`. Identical evidence updates only latest.json; it does not fabricate another improvement. `record_task_outcome` requires the current task generation and the actual human verdict. Protocol completion never marks owner acceptance. Tests/probes stay separate. Missing historical data, total task/team token cost, admission/retry counts and causal benefit remain explicit gaps.

Runtime 0.4.6 fetches feedback for exact hosted task IDs mapped to local generations in the selected window, including older tasks continued recently. Requests use batches of 100, without a total lookup cap or a scan of unrelated hosted history. Coverage states requested/matched/missing jobs, batch count and ordinary runs with remote metadata. A mismatched response or failed batch makes sync unavailable rather than complete. Unmapped local records and verdicts absent from retained generation history remain unknown. Empty-body callers retain the older recent-100 endpoint behavior.

The review includes observed approval/question counts and verified per-generation permission metadata where available. An interrupted ordinary-work run with approval requests, no question requests, and at least five minutes of human wait produces an investigation candidate immediately. This is a delivery warning, not an owner verdict or permission to approve anything. Check the actual task and delivery state before concluding why it happened. The daily reviewer must itself use `gpt-6.1-sol` with `xhigh`; the attached chat's actual scheduled turn metadata is the verification source, not a model name written in the prompt.

The daily review may make one bounded, evidenced harness improvement with regression checks and the existing main/publish workflow. Changes to owner model/effort, auth, permissions, unrelated products or increased caps need a fresh owner instruction. Existing task history and active owner work remain protected.
