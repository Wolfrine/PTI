# Recycled terminal worker PID

Evidence: the daily review found remote task `915dd95cc28da2eb7f99371eea0d42fe`, generation 4, claimed since 2026-11-03 03:43 UTC with no local task attached. Its prior local generation (`28aeecaa763d370dcaa68c68e33af9ff`, generation 3) completed on 2026-11-01 at 12:32:49.753 UTC. The historical worker PID 8720 now belongs to another Node process created on 2026-11-02. The terminal continuation guard checked only whether that number existed. It therefore treated an unrelated process as the previous worker still exiting and retried without starting the queued generation. The listener and authenticated health maintenance remained connected; the generic local unavailable status did not establish an authentication defect. Cumulative failed-loop counts cannot all be attributed to this one observed case.

Hypothesis: compare process lifetime with the terminal task timestamp before applying the existing exit guard. A process created strictly after that terminal timestamp cannot be the prior worker. This removes a false block without cancelling, killing or changing unrelated work.

Bounded change: `worker-lifetime.mjs` probes only the selected numeric PID's birth time through a hidden Windows process query. The `continue_task` guard permits the proven recycled-PID case. An actual prior process, equal timestamps, or unknown process/timing metadata retains the existing wait. Missing PIDs need no probe. Request key, task/generation, native-thread identity, locks, current scope and model/permission validation are unchanged. This is not a new count, duration or nesting restriction. The plugin package is unchanged; runtime version is 0.4.5.

Regression risk: incorrect lifetime parsing could permit continuation before a real worker exits. Unit checks cover later, earlier, equal, missing and unknown timing; the real Windows probe checks a live test process. The MCP fixture leaves an unrelated process alive, assigns its PID to an older terminal record, then completes same-thread continuation and human-response recovery. The full 51-test worker suite, build, Home contract and diff checks pass. These are fixtures and source checks, not owner acceptance or a production billing measurement.

Activation and recovery must preserve both active owner claims and the unrelated process. Prefer an idle installation. A targeted recovery may replay only the exact already-queued generation through the corrected server, using its existing request key and original durable request in memory, without starting another outcome or changing generation. Do not cancel/restart other work merely to activate this release. Record the actual retained/revised/rejected delivery result under the F-drive bridge harness/reviews directory.

Retain the source correction when failed-case and prior-success checks pass. Roll back the scoped guard through main if it misidentifies a prior live worker or breaks same-identity continuation; preserve task history and never kill a PID on the strength of its old numeric value. Keep unknown cases explicit rather than fabricating a successful recovery.
