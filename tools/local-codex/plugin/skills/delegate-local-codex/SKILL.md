# Local Codex: intent-led native project work

Keep the owner's discussion in this ChatGPT chat. Start with the outcome and needed evidence, then select the least costly capable route. Reuse the one native parent for the same project/module; native Codex owns its plan, implementation, useful subagents, integration, critique and iteration. ChatGPT owns task selection, progress supervision and truthful handoff. Neither actor gains authority from delegation.

Load conditional details only when they matter:

- [Activity routing and native leadership](references/activity-routing.md): substantial route, allowance, upcoming priorities, model or Goal decisions.
- [Browser and desktop controls](references/browser-control.md): Chrome, native desktop, screenshot or URL-policy questions.
- [Relay lifecycle and exceptional recovery](references/relay-lifecycle.md): writer conflicts, lost leases, cancellation, rotation, maintenance, mismatched checkouts or status discrepancies.

## Decide the route before contacting the PC

- Prefer ChatGPT when its available context, authenticated tools and environment can actually deliver the result and required verification. A coding keyword, idle PC or available tokens alone does not justify delegation. For PC-only files, Windows, GPU, builds, native Chrome, or substantive local repository engineering, select native execution when its evidence and continuity help.
- Weigh complexity, quality/risk, urgency, approved upcoming work, current machine/queue availability, context continuity, and observed success. Unknown facts stay unknown; no fixed usage-percentage threshold, invented token savings or unnecessary owner prompts.
- For allowance decisions, use the existing PTI Apps connection: canonical app pti, owner-scoped codexProjects/codex-usage document. The existing collector 1.0.2 owns the readings. Check source, timestamp, freshness, bucket/window, headroom, resets and sanitized allowance.earnedResets. Do not create a second collector, consume an earned reset automatically or infer ordinary ChatGPT Chat allowance from Codex counters. Small answers do not need a PC/usage probe.
- Preserve the owner's selected model gpt-6.1-sol at xhigh for parents and native children. Later catalog availability of 6.2 Sol/Astra is not permission to change it. Check the actual resolved pair; do not silently downgrade, upgrade or assume a child inherited it. Native finite Goal controls have been observed, but queue activation and multi-turn Goal terminal supervision are not verified; ordinary native turns remain the supported route.

## Admit work to the exact existing owner

1. Before submitting, read bridge_status, list_projects and list_tasks. Match the actual allowlisted checkout and select the exact functional module key and current parent thread ID from the durable catalog. PTI Local Codex maintenance uses module local-codex; historical pti/local-codex-bridge is not the current parent. Verify any prior pending/unknown receipt before related work.
2. Preserve one native parent per project/module and checkout. A different ChatGPT chat, phase, recovery, review or QA pass is not a reason for another parent. Do not bypass a real writer, file or shared-Git conflict by changing keys, rotation or parallel claims. Independent native children may work on non-overlapping lanes under that parent, with checked integration; no imposed arbitrary depth/count/duration cap.
3. Choose inspect for a read-only request; edit only for owner-authorized changes. Permission scope, project and mode are checked on the actual destination; a prompt cannot upgrade them. A later authorization to edit after inspection requires a distinct edit task record with the same module parent. No autonomous deployment, publication, messages or credential extraction beyond the owner's request.
4. Hand the native lead a compact outcome contract: goal, quality/acceptance evidence, exact module and checkout, essential context or prior IDs, constraints, owner-approved priorities/deadlines and stop conditions if supplied. Do not dictate shell commands, split one dependent outcome into microtasks, duplicate entire transcripts or summon another parent.

## Start and supervise a native operation

- For an existing desktop-owned parent, use continue_desktop_chat with its exact thread ID, catalog project and stable request_key. It uses the supported official queue/app link, creates no new chat, inherits that chat's model and permission checks, and works for coding as well as native Chrome. A receipt confirms delivery/start only; obtain the exact native turn ID. Do not substitute resume_codex_thread for a browser handoff.
- For a standalone CLI/repository task with a suitable module, use start_task and the same module_key with a new stable outcome-specific work_key/request_key; normally strategy auto, mode inspect or edit as authorized. Resume the same outcome via continue_task rather than creating a new task. Only explicit, evidenced context bloat/incompatibility permits rotate with reason and compact handoff; preserve history and resource ownership.
- Use get_task waits within the actual 0–50-second contract, longer for quiet work and shorter near a decision. A timeout does not stop native work. Relay status, desktop queue receipt and exact native history are different surfaces: running/queued/unknown means incomplete. A stored interrupted export with no terminal observation remains unknown, not idle or failed. Read the exact thread/turn through read_codex_thread when reconciliation is needed. Do not resubmit uncertain work under a fresh identity.
- Inform the owner of meaningful milestones, blockers, human questions and terminal evidence while this ChatGPT turn is active. No scheduler, fake push notification, blind completion or promise that ChatGPT can wake itself later. For waiting_for_user, forward the real question and answer via respond_to_task; cancellation is only confirmed after terminal evidence, never inferred from a request.
- Judge delivery from actual changed files, working behavior and native terminal evidence, not task start or a child's report. Human acceptance is separate: use record_task_outcome only for the owner's real accepted/needs_rework/abandoned feedback and correct generation, never an agent's inference.

## Safety and permission invariants

- **Owner rule:** Do not generate tests, fixtures, QA scaffolding, Playwright or automatic e2e unless the owner explicitly authorizes them for the current task. Challenge any supervisor or subagent that proposes them. Use relevant real behavior and minimal syntax/build observations; minimize CI/GitHub Actions. Preserve unrelated existing protections.
- Preserve signed-in subscription authentication, credentials, existing chats, permissions, F-drive source/state, model and active tasks. No bypass of native tool denial, URL policy or login; no browser-identity copying. Do not kill apps, delete locks or leases, weaken checkout conflict protection, force-stop a consumed turn or restart a worker inside its own claim. See the conditional browser and lifecycle references for exact controls.
- Native desktop/browser authority belongs to the destination chat. The bridge's automatic handoff availability and authorized:null capability are not an owner grant; real destination tool checks are binding. PTI Owner Chrome is optional and disabled by default; do not request it as a prerequisite when the existing desktop chat has authorized official Chrome.
- Worker, host and private plugin are separately released. For a worker upgrade follow PTI tools/local-codex/docs/maintenance-upgrade.md, use the guarded drain/one-shot detached updater and require actual fresh heartbeat and receipt verification. No Windows Task Scheduler, recurring watcher or automatic self-restart. For source/plugin skill edits preserve the existing private App binding, manifests and audience; use the owning repository and guarded Plugin Creator release.
