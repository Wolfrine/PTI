# Browser and desktop verification

Use official browser/Computer Use tools available in the executing native turn. Enter through their documented normal entry point and permission checks. Runtime Full Access, installed Chrome, extension health, a connected relay or environment metadata alone does not establish browser control.

## Choose where the browser step will run

Local Codex starts or resumes a standalone app-server. Opening a new thread or granting Full Access supplies no desktop browser connection. When the owner specifically asks whether that worker can browse, exercise its official tool once and report the worker's own result.

For a browser-only request, use an official browser already connected to the requested PC in the requesting conversation. Check which browser and profile are available, then perform the requested interaction. A cloud browser is a different environment. If the PC browser is unavailable, use the desktop app or connected-host Remote entry point when available and authorized. Avoid starting another relay task just to repeat a known host failure.

For implementation that needs browser verification, keep the code and fixes in the selected native thread. Arrange the browser check before dispatch, perform it against the actual revision when ready, and identify which session observed the result. Pass the relevant observation and permitted artifact reference back through the existing task when needed for a fix. Attribute caller observations to the caller. Tasks requiring independent play or review still need the requested reviewer.

When only an app-owned continuation can perform the check, finish the relay turn first. Provide a link to the observed native thread using `codex://threads/<thread-id>` and the exact remaining action to run with `@Chrome` on the PC. A link opens the conversation. Browser access is established by a successful action in that desktop turn. Keep the browser-dependent outcome open until the requested action succeeds. Respect a denied target across sessions and controllers.

## Conduct the check

1. Honor the requested browser, profile and environment. Use the official connected tab/browser API for navigation, interaction and screenshots when available. Use native app input for native controls only within that controller's policy.
2. An absent official tool leaves the exact browser/desktop step unavailable. State the omitted check and continue independent coding or investigation. Do not automatically transfer work to another chat, install a provider or ask the owner to perform routine navigation.
3. An actual host-unavailable, URL-policy or tool-denial response ends the rejected action. Do not retry through another controller, shell input, URL rewriting, copied profile/identity/pipe, raw CDP/Playwright or changed security policy.
4. Observe the actual target and requested behavior. Login, 404, expired access and capture failure are specific findings. Navigation, a build, a heartbeat or a source patch alone does not establish visual, gameplay, audio, device or authenticated-flow acceptance.
5. Return real artifacts through their owning tool when possible. Textual history can omit screenshots, attachments and tool output. If an artifact cannot be retrieved or inspected, report that evidence gap.

PTI Owner Chrome, the interactive-QA broker and desktop-chat handoff are retired from the 0.5.0 execution path. Their old decision records preserve historical evidence and do not grant current access. Browser availability is optional to transport operation; a task whose acceptance requires browsing remains unverified until that real check is performed.
