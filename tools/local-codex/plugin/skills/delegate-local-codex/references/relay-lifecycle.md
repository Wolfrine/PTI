# Local Codex relay lifecycle and exceptional recovery

Load only for writer conflicts, failed or uncertain handoffs, native-history disagreement, cancellation, checkout mismatch, module rotation, maintenance or access diagnostics. Ordinary tasks use the short delegation skill's admit/start/observe contract.

## Identity and module ownership

- The current human request sets scope. A project key maps to one authorized physical checkout/resource path. list_projects returns durable modules with exact module_key and current parent thread_id, even after their tasks disappear from list_tasks's recent window. Check bridge_status, list_projects and list_tasks before starting native work.
- Select the module by established functional ownership, not a title fuzzy match. PTI Local Codex maintenance uses local-codex; pti/local-codex-bridge is historical. A new task/phase/ChatGPT conversation does not itself justify a new module or parent. Different repository names can share a Git working copy, so coordinate same-file and shared-Git writes.
- If no module can be safely established for a genuinely new project/function, do not invent one from a title. Omit it only where the standalone tool permits, and disclose that this may create a new parent. A confirmed missing/deleted/archived or incompatible automatic parent must be resolved from actual records, not rotated merely because of transient ownership contention.
- Retain the selected project, module key, task ID, generation, work_key, request_key, native thread, queued submission and native turn ID. The retry of uncertain delivery must use the exact original request_key and inputs. A new outcome may have a new work_key and task record under the same module.
- For native desktop-owned chats, prefer continue_desktop_chat with the exact parent. It uses the native queue and app link; permission/model are owned by that chat. For eligible standalone CLI/repository work, use start_task with the existing module_key, explicit inspect or edit mode, stable outcome-specific work_key/request_key, and strategy auto unless small single work or independent lanes justify another strategy. continue_task resumes the same outcome.
- An inspect task stays read-only. A separate explicit owner authorization to edit after inspection needs a distinct edit task record but the same suitable parent. An existing chat's edit permissions are not a permission grant for an unrelated request. If project/mode, destination permissions or checkout disagree, stop and reconcile before further input.
- The owner requests no arbitrary thread-count override, branch or worktree creation for convenience. Preserve checkout affinity, especially when another module shares its Git directory. A returned reused:true record may require an explicit follow-up submission: inspect followup_required before claiming the new work was delivered.
- Do not impose arbitrary bridge agent-count, nesting, duration or age ceilings. Use parent-led native subagents for genuinely independent, non-overlapping lanes, with same verified model/effort and parent integration. A busy module or active writer is ownership, not evidence of context incompatibility.

## Desktop queue, liveness and history

- A desktop handoff operation may initially report queued. A result.state started plus exact turn_id proves the queue consumed input and native turn began; it does not prove completion. A dispatch receipt or returned app link is only delivery evidence. Worker 0.4.14 supports bounded observation across native turns, but only exact native terminal evidence completes a handoff.
- Choose get_task.wait_seconds from 0 to 50 according to expected work and responsiveness. Quiet long tasks can use longer waits. Heartbeat is worker liveness, not native progress; a timeout does not stop work. Respect actual tool schema and client timeout; do not invent a limit based on older clients.
- get_task/list_tasks contain bridge-generation records and exact bridged turns, not arbitrary later desktop-app turns. read_codex_thread is an asynchronous, non-model read; poll its separate operation ID via get_task and check cursor/truncation. Exported history omits tool outputs and attachments. Comparing old bridge-only attempts to a later app-owned desktop turn without exact IDs is invalid.
- A separate reader may export an ongoing desktop turn as interrupted even while native work continues. Without a native-terminal-event, a completed_at timestamp or actual live terminal observation, classify the turn unknown—not failed, stopped, idle or available for a new writer. Compare exact turn_id, last activity and native final messages. Do not republish a completion or free ownership based on a stale export.
- The official queue can retain unconsumed input behind an existing desktop writer even if its initial bounded startup observation times out. Never resend uncertain pending input under a fresh identity or rotate parents to force progress. Reconcile the original receipt and turn.
- If history reading fails after durable delivery, keep the outcome unresolved; a reader failure cannot undo the native command. If a bridge lease expired, maintenance may safely mark that hosted generation interrupted while preserving unknown native outcome. This is not permission to requeue, cancel or stop native work.

## Remote-control start and pairing

- `start_remote_control` and `pair_remote_control` are **host-only** operations, independent of project checkout, module parenting and desktop queue ownership. Both use fixed commands under the PC's existing ChatGPT subscription sign-in: `codex remote-control start`, then `codex remote-control pair --json` for a requested manual code. The helper checks `codex login status` first. Do not supply custom argv, shell, path or credentials, or bypass a CLI unsupported/authentication/daemon error.
- Each host tool returns an **operation ID**, not the daemon or pairing outcome. Poll that exact ID through `get_task`. A `start-command-succeeded` or `process-still-running` receipt means only the bounded start attempt completed/continues; neither proves a phone is paired. Only a `code-created` result with `manualPairingCode` authorizes sharing that current code with the owner, along with `expiresAt` when provided. It does not establish that mobile authorization succeeded.
- Codes are short-lived and their stored receipts are redacted at expiry (at latest within ten minutes; the helper defaults to five minutes when expiry is missing). Treat `state:expired` or `redacted:true` as unusable, and never repeat an old code from chat/history after expiry. A fresh code needs a **new request_key** after checking the prior operation; replaying an uncertain attempt under the same key does not safely regenerate one. Do not infer or promise a QR code, OAuth completion or phone connection from the CLI operation. Actual pairing is confirmed by the remote client/device state.

## Writer and checkout conflicts

- A native active-writer error is not proof of a stale lock. The current worker may attempt supported same-chat queue recovery only when an uncancelled edit's standalone attempt failed on ownership before any tool or native turn ran and its worker exited. Preserve the original task/generation/module, permissions and audit. Inspect tasks do not silently broaden to desktop edits.
- If standalone recovery is terminal or unsupported, first establish non-delivery and exact thread ownership. An explicitly authorized handoff of that same task may use the known desktop parent and a stable key tied to the failed record. Never spin up a second parent or omit module_key to evade contention.
- Documented independent daemon/proxy stop access on the inspected PC failed with Windows socket 10050. An independent reader's thread/unsubscribe notLoaded does not release a desktop writer. If supported native stop is unavailable, preserve the queue and wait for native completion or report an unresolved blocker. Do not kill an app, delete a lock, manipulate a lease or claim a consumed turn was stopped.
- Checkout affinity must match the real resource path. If a native saved chat reports a managed worktree or another cwd, compare the exact native thread's cwd and list_projects resourcePath. A matching repo title or shared Git directory is insufficient. Resolve owner-authorized destination before submission; retain failed identity and thread for audit. Do not silently retarget/retry a failed generation or rotate as a workaround.
- Archived or confirmed missing threads require explicit reassessment; notLoaded may be resumable, while deleted/invalid/incompatible ownership may need an evidenced replacement. When context is genuinely bloated/invalid/incompatible, use an explicit module and new task/work key with chat_policy rotate, supported rotation_reason and compact handoff. Preserve predecessor IDs and history. No automatic rotation by turn count, token count, age or arbitrary task phase.

## Cancellation, owner questions and acceptance

- waiting_for_user requires the exact human question/approval; respond_to_task forwards only the owner's actual answer. Do not substitute inferred permission. Cancellation must be observed through a terminal state. For consumed desktop input, cancel_task may remove only pending queue entry; a stop.state unavailable means no native interruption happened and observation continues.
- After a cancellation or fault, distinguish source edits already performed, native work still running, and final delivery. No claim of rollback from a cancel request. Human accepted/needs_rework/abandoned feedback belongs in record_task_outcome with the correct task generation; task completion, an agent's rating and silence are not acceptance.
- For code or browser work, return actual outputs, deployment/check evidence and explicit limitations. If final response was truncated, read the exact native turn/history or artifact rather than inventing contents. Keep user updated only while this ChatGPT turn is active; no scheduler, fake push channel or promise to wake later.

## Maintenance and source releases

- Windows host, worker, native Codex app and private ChatGPT plugin are separate components with distinct versions/contracts. Recheck live bridge_status before relying on a version. The owner has authorized `gpt-6.2-sol/xhigh` by default and explicit `gpt-6.2-astra/xhigh` for demanding work, but the live Windows `config.json` and existing desktop parents must be migrated/verified independently. Model catalog support or Goal-control availability alone does not prove the native task used the new model or that Goal-aware supervision works.
- For worker changes use the owning PTI tools/local-codex/docs/maintenance-upgrade.md. Maintain the hosted transactional drain fence, stage exact artifacts, arm only the guarded bounded one-shot detached updater after the owning task releases its claim, and require an activated-verified receipt plus fresh local/hosted heartbeats. A staged helper or source commit alone is not activation. During drain, new claims are blocked; interrupted installation retains its fence until verified recovery. Never self-restart from inside the active claim, kill the listener, delete another task's lease or create recurring Task Scheduler/ChatGPT waits.
- Keep Git repositories/code on F:; runtime/release files, logs, reports, receipts, caches and models belong on H:. Preserve legacy F: operational state/rollback until guarded migration is verified, and keep native app-managed credentials/history in their required protected platform locations. Source/instruction edits must use the canonical repository and release path; minimize GitHub Actions and verify ownership/active dependencies before relocation. For app-backed private plugin skills, preserve plugin ID, App binding, MCP tools, audience and manifests; publish through the guarded Plugin Creator release with readback verification, not through browser-session extraction.
- A relay/plugin change is not proof of native behavior. Validate against an actual prior failure and successful scenario: browser authorization, writer ownership, stale interrupted/expired lease and ordinary delegation; use only direct observed checks and minimal syntax/build, not AI-generated tests/fixtures/Playwright/e2e without specific owner approval.
