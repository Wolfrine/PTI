# Auto Edit v1 — worker foundation

This is new, isolated source code for the owner-approved automated editing and review workflow. It is not the retired Auto Review implementation and is not wired into live worker admission.

- auto-edit-contract.mjs: immutable device-bound configuration, explicit authorized source set, bounded selection without replacement, numeric seeds, folder and provenance validation, exact prompt composition, vision result and staging receipt validation.
- auto-edit-runner.mjs: one-item slices, fresh authoritative claim/command checks, stage checkpoints on H:, durable writes, resource guard callbacks, pause/stop boundaries, output hash verification, uncertain edit/delivery reconciliation, compact progress publication, and error separation.
- No cloud credentials, cloud image chunks, new scheduled jobs, network services, model downloads, or additional package dependencies.

## Integration boundaries

Bind the coordinator to the current approved worker's single-device dispatcher. The dispatcher owns Firestore listeners, conditional claims and writes, cancellation propagation, manual-job fairness, actual resource checks, and device revocation. Claim returns the current approved/owned status, command and monotonically increasing revision; an optional retryItemId on a new run command authorizes retry at a safe boundary. The publisher must fence each write against the current claim and treat replay of journaled metadata as an idempotent update. Do not mark a command acknowledged merely because it has been observed. The adapters must verify the current authorization of each source and restrict access to approved original folders; they must not treat a folder location as evidence of consent. The source adapter reads original bytes and validates actual Drive identity. The editing adapter uses the selected existing local inference engine and the engine's existing consent, resource and execution requirements. Vision adapters must produce the bounded structured results defined by the contract. No new model instructions are defined here.

The worker must only reconcile an interrupted edit as saved when the exact output, model/seed, original hash, effective prompt hash, engine revision, dimensions and steps are confirmed. The coordinator validates the receipt and the local PNG hash/dimensions. A not-started recovery result must be explicitly confirmed; unknown outcomes block rather than resample. A delivery adapter must reserve a stable Drive file identity before uploading, verify the destination and content hash, and return the exact existing receipt on retry; unknown outcomes block rather than repeat side effects. The current staging folder is verified; accepted-output move and Auto Generated folder provisioning are separate owner-review work.

Auto Edit checks for 18 GiB of available RAM before downloading a pilot source and again before starting new Turbo inference. The in-flight Qwen guard still stops at 5 GiB available. Manual Studio continues to use its existing preflight.

The journal stores only authorized batch metadata and original/output hashes. The original and edited image files remain in H: runtime storage; publication contains private metadata, never raw image bytes or local paths. Keep recovered artifacts until delivery/review needs are satisfied. No cleanup of private originals or staged outputs is performed by this foundation.

## Firestore bridge and live progress

The new `auto-edit-firestore.mjs` uses the existing approved PC `Queue` session. Batch documents contain the immutable plan/hash, owner command and command revision, one device claim, dispatch flag, and worker execution snapshot. Item documents preserve exact prompt provenance, stages, durations, observations, model/seed, and verified output receipts. Parent and item publication is atomic and conditional on the current Firestore document version. A publication revision fences replays and prevents a missing/older local journal from silently re-running completed work.

Create rules validate the whole item against the plan. Update rules keep the source and configuration immutable and validate changed metadata, including any receipts affected by artifact changes, within the atomic write's rules expression limit.

The optional server-snapshot queue listener wakes on new work or owner command revisions; ordinary progress updates do not wake it. The one-item dispatcher is designed to run under the existing worker lock, with manual-job arbitration. Resource samples use a separate revision-fenced document, every 25 seconds only during an active in-flight stage. The UI should show only samples matching the current execution revision and active item. Completed stage and prompt data remain available after the run.

Rules source defines a new owner-scoped namespace and defaults to closed admission. Source changes have not been published to live Firestore. The current worker main loop is not yet activated for Auto Edit: concrete local model/Drive adapters and notification lifecycle binding still need verification. No model loading, image transfer, independent credentials, new services or idle polling are introduced. Do not enable admission until an authorized single-item roundtrip has been verified.


## Local preparation and resource preflight (Phase 4C)

`auto-edit-local.mjs` is a fresh, non-inference adapter foundation. It calls the current Qwen diagnostics evaluator in the existing Python environment to check available RAM, F:/H: free space, GPU memory, temperature and required observations. The existing thresholds are unchanged. A failed or unavailable measurement blocks the stage with a specific error code.

The original-byte reader requires an independently authorized Drive metadata resolver that correlates the exact file ID, parent, MIME, byte count, checksum and local mount path. It accepts only direct children of the two verified original folders and rejects unknown mappings, changed identity, symlinks and checksum mismatches. Local copies are constrained to the H: Auto Edit workspace, streamed through bounded buffers, hash-verified and published without overwriting existing copies. Source images are never modified.

Remaining dependencies: establish the precise currently installed vision executable/model/projector paths, verify the owner's supported unattended Drive file-ID/checksum resolver and confirmed staging delivery, and check the H: runtime directory access permissions. The local reader requires that actual resolver before it can be bound; a mounted filename is not a cloud identity receipt. Do not transfer OAuth secrets to the worker, loosen existing consent/security controls, or infer image authorization from folder membership. The actual local model adapters, Drive delivery and worker lifecycle wiring remain disabled and unimplemented. No earlier retired workflow is used. Verify ordinary authorized editing with a separately approved practical run before activation.


## Local model runtime binding (Phase 4D)

`auto-edit-models.mjs` binds Vision 1 (2B) and Vision 2 (4B) to the audited local llama.cpp installation through `auto-edit-runtime.py`. The launcher uses local file/hash pins, a disposable process, the existing H: inference lock and Qwen resource guard predicates. It runs a bounded descriptive or comparative image-quality task, with strict JSON output validation. Source and edited images are verified against the coordinator's recorded SHA-256 before model use. Prompts stay in private runtime storage and are not passed as command-line arguments.

The image editing adapter uses the existing Studio engine and its reference contract, preserving the original bytes and preparing a bounded, aspect-preserving local reference. It records the exact engine request and normalized-reference hash before inference. Existing engine markers and result metadata are reconciled against the source, prompt, seed, model and output bytes; an unknown interrupted edit is not repeated.

Activation requires a locally provisioned and integrity-verified installation, protected workspace and model/runtime paths, existing worker authorization and Drive adapters. The new code does not enable admission or start any inference by itself. Windows process containment, cold model start, output parsing, actual resource release and original/edited delivery must be verified in an explicitly authorized practical run. No retired Auto Review code is used.


## Phase 4D — desktop Drive and worker integration

The metadata-only `/api/drive/auto-edit-metadata` operation is part of the existing Velum Drive function. It accepts only the pinned, currently approved Firebase PC and the active, owner-authorized batch item; it checks current admission and execution revision before returning exact source metadata or verifying a staged output. It returns no Google OAuth credential or image bytes. The desktop adapter copies original bytes via the verified J: mapping, checks independently supplied hashes, writes one deterministic staging filename, and reconciles its actual Drive ID/parent/checksum. A missing cloud sync receipt or partial/ambiguous copy blocks the item; it does not authorize another upload. Unlike the manual browser reserved-ID route, desktop delivery reserves a stable item/name locally and obtains the real Drive ID only after verified sync. No media is transported through the Function or Firestore.

The current worker starts Auto Edit only after explicit local installation provisioning and server-confirmed admission. Manual work has priority at item boundaries. The extra queue listener shares the existing authenticated SDK connection, closes on revoked admission or device authorization, and only dispatches on a relevant server event or a bounded retry of active work. The existing heartbeat reflects an active Auto Edit slice without inventing a manual job. Stage records and resource telemetry continue to use the separate Auto Edit namespace.

Local installation is intentionally not created by application code. Its exact path is H:\Workspace\Generated\Velum\auto-edit-v1\installation.json. Provision version:1, enabled:true, visionPins (the five exact binary/model/projector paths relative to the fixed audited vision runtime mapped to independently verified SHA-256 values), folders (the two verified Drive folder IDs mapped to actual absolute J: directories), and stagingRoot (the verified Review staging child). The root/config and engine output privacy ACLs, model/runtime integrity ACLs and parent deletion permissions must be verified before work starts. Do not alter shared directories or permissions without explicit local authorization. A missing/unsafe installation leaves manual Studio available.

Source integration is not live validation. The existing Drive metadata grant, actual Desktop paths and sync semantics, Windows ACLs, model child containment, cold vision JSON output, Qwen output/recovery and reviewed Firestore rules all require authorized verification. No new cloud service, schedule, model download or test suite has been added. The existing Drive function change has not been deployed; evaluate incremental metadata request usage and obtain any required cost approval before release.


## Phase 4D — local provisioning corrections

- Windows launcher identity: `auto_edit_lineage.py` verifies the actual live Node parent and its creation timestamp. It allows only the configured Python venv executable as a single intermediary; other ancestry, PID reuse and vanished launcher/worker processes fail closed. Both the resource probe and vision wrapper use this check. The vision guard revalidates the same process chain during execution. Existing resource thresholds and device authorization remain unchanged.
- Disabled configuration: the installation loader can read a bounded, explicitly disabled configuration without attempting activation ACL checks. An enabled installation still requires the original workspace, parent, vision integrity and engine-output permissions, plus a consistent config readback. Errors identify workspace, vision or engine-output permission categories. Shared-directory ACL remediation remains a local provisioning action, not an automatic permission change.
- Drive delivery: the durable H: intent now distinguishes prepared and potentially started writes, and pins any independently observed Drive file ID. The existing metadata service may report a verified partial-file identity/checksum but never a completed receipt for it. The desktop worker can resume only the existing same-name file, only when the observed Drive prefix and every mounted byte match the immutable, verified H: output. It appends missing bytes without truncating or replacing the file. A missing mount after possible creation, mismatched prefix, different Drive ID or ambiguous cloud state blocks recovery; it cannot trigger a second upload or model execution. Final delivery still requires the exact full SHA-256, size, staging parent and stable Drive ID. No media bytes or credentials are sent through the metadata route.
- Remaining live gates: synchronize this source to the PC; verify exact launcher ancestry with the existing no-model resource probe; remediate the narrowly scoped ACL issues without weakening protection or modifying unrelated shared directories; run source syntax/build checks; verify actual DriveFS append and sync behavior using separately authorized delivery verification before activation. The updated function must be deployed with reviewed authorization/cost controls before the partial-status response is available. Source changes alone do not enable admission, restart services or prove an end-to-end run.


## First live release — one-image pilot admission

The initial live release accepts only an explicitly authorized one-image Turbo batch. Ordinary batch admission is deliberately unavailable until the later Studio release. The owner-only control document `autoEditControl/admission` accepts the disabled shape `{version:1,enabled:false,updatedAt}` or the enabled pilot shape `{version:1,enabled:true,updatedAt,mode:"pilot",batchId,sourceFileId,expiresAt}`. The expiry is at most three hours ahead. The rules, worker and metadata broker all require the same immutable batch ID and original Drive file ID; the worker subscribes directly to that batch document rather than opening the general queue. The worker closes its listener and aborts the active slice on expiry or revocation. General admission is not enabled by this change. Use an explicitly approved existing, non-personal ordinary image and ordinary edit for live verification; do not infer consent from directory membership. A pilot result is not proof of general production readiness. The operator must close admission and disable the local installation after the pilot. No new service, scheduling, image generation, cloud write or deployment occurred as part of this source change.


## Phase 5 — Studio pilot interface and owner review

The new Auto Edit tab is independent of manual Create and Creations. Its configuration, original picker, explicit owner authorization, one-image Turbo submission, immutable approved revision, batch, and expiring admission are atomic. The worker advertises a fresh, timestamp-bound readiness marker on the existing heartbeat, without a new idle polling path. The browser/worker share the canonical plan serialization; browser SHA-256 matches the Node plan hash. The PC continues after the browser closes. The browser listens only while Auto Edit is visible, scopes live progress to the selected batch/item and active resource document, uses a bounded 20-batch history, and releases all comparison URLs and listeners on lock or exit.

Owner review requires the recorded original and edited bytes to match their verified Drive checksums. Press/hold peeks at the original; release returns to the edit. Okay and Not Okay create one immutable review record. Not Okay remains in staging. Okay is a pending decision until the existing Drive function confirms the same file was moved from the pinned staging folder to the private, exact Auto Generated folder. Folder creation reserves a stable Drive ID before any create. Existing move lease/receipt handling serializes and reconciles the same file on retry; an ambiguous move never generates another image. The server records the confirmed destination only after identity, parent, byte count and checksum verification. Gallery Sync discovers only accepted outputs whose review receipt and Drive metadata match; original selection remains limited to Private / References. Manual gallery folder moves do not apply to accepted output records.

Phase 5 is source development only: owner has requested to perform practical verification personally. General batch admission remains restricted to a single exact image until owner acceptance; model is Turbo and batch size 1 during pilot. Config revision restoration and evidence-based learning belong to Phase 6. Latest UI/rules/function/worker source requires build, live rules review, PC sync, scoped release and owner verification. No inference, live deployment, new test suite, scheduled job or new cloud service was executed or created.


## Phase 6 — local learning and immutable configuration history

The owner approves a configuration revision either through the composer Save action, an explicitly submitted pilot, an explicit learning approval, or an explicit historical restore. Each new immutable `autoConfigs/{revisionId}` records its parent, approval time, reason and kind; a restore creates a new revision referencing its historical source. `autoEditControl/currentConfig` changes atomically with the new revision. Existing pilot batches retain their exact immutable config snapshot. Submitting identical settings reuses the current revision, so accepted and rejected examples can accumulate under it. Loading a configuration into the composer is a draft action only; it never authorizes a reference image.

Learning is an owner-requested one-shot operation in the same worker and resource arbitration. Select one or two final reviews from the current exact configuration and model, explicitly authorize local analysis, and close the previous image pilot before requesting it. The same existing admission document admits either one exact image pilot or one exact `autoLearnings/{learningId}` request, never both. Learning admission expires after at most 30 minutes, and the PC listens only to the named request. The assigned device may read only the named item/review evidence and base revision through the learning grant. No gallery scan, new listener at idle, cloud image bytes, new service, scheduled work or independent GPU queue is introduced. An interrupted running claim fails rather than repeating an uncertain inference.

The pinned local Qwen3-VL 4B model uses the already retained, checksum-verified original/edited pair of the first selected reviewed example plus bounded recorded observations and feedback from up to two same-revision examples. It never regenerates an image, rereads unrelated private files, or performs automatic training. Each result stores the exact evidence IDs/hashes, local model identity, bounded task evidence digest, observations, hypotheses, confidence and limitations. Its machine-actionable recommendations are limited to ordinary image-quality and preservation keys; free-form model observations never become instructions automatically. The UI shows the source evidence and lets the owner select recommendations, edit proposed instruction/guidance text, approve a new immutable revision or reject. Approval requires the original base still be current; stale proposals cannot replace newer revisions. Cancelling, failing, rejecting or expiring learning cannot change configuration.

Current release remains a single-image Turbo pilot; no general automated batch admission. Owner retains practical verification. Source-level integration, compilation, reviewed Firebase rules/worker/Hosting deployment and actual local model behavior are separate release gates. No images, inference, live writes, new test suites, deployment or scheduled jobs were executed during Phase 6 source work.

## Phase 7 — release integration hardening

The PC reports Auto Edit readiness only after a server-confirmed admission snapshot. A failed listener clears readiness and uses the existing bounded reconnection mechanism; a fresh confirmed snapshot restores readiness. No independent polling or scheduler is added. Pause/stop publications include the affected pilot item even if no active item was supplied by the resumed dispatcher. Terminal completion wins over late pause/stop commands rather than causing repeated dispatch; completed-with-failures accepts only an explicit checkpoint retry. The corresponding browser control and Firestore rule are aligned. This is source-only integration hardening: the owner retains the practical image verification. Latest release compilation, live rules reconciliation, exact PC revision sync and affected-component deployment remain outstanding.

## Configurable Vision 1 instruction

Studio exposes the complete editable Vision 1 observation task in the configuration panel, with a reset-to-default button. The shared default requests concise visible silhouette, general proportions and posture preservation, not environment or unrelated details. The existing `visionGuidance` wire field is retained so the instruction is included unchanged in the approved configuration, immutable batch hash, revision history and editable learning proposals. New composer drafts start with the default; loading an old revision preserves its exact value. A blank instruction explicitly requests no Vision 1 addition. The worker combines the selected task with fixed ordinary-edit, privacy, authorization and JSON output constraints; it does not permit instructions to replace those constraints. Prompt provenance shows the stored Vision 1 task as well as its returned addition, limitations, original edit instructions and final effective prompt. Vision 2 stays unchanged. No runtime inference or deployment occurred during this source update.

The Vision 1 adapter now passes the immutable owner observation instruction directly as `observationInstruction`, with the edit instructions as separate context. The local runtime validates both parameters and applies the unchanged authorization/privacy/response constraints independently. No generic observation task is hardcoded in the adapter. Vision 2 and learning requests are unchanged. This source change requires the final release plan to be refreshed before deployment.
