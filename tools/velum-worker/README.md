# Velum PC worker

Studio accepts explicit text-to-image and reference-image requests for the installed models through the owner's existing PTI Firebase project. The phone talks outbound to Firebase; it never connects to a PC port. Drive gallery reads remain separate from an explicit browser-side Save to Drive grant. There is no prompt enhancer, hidden suffix, aesthetic correction, content-based negative prompt or automatic gallery save. The owner is the visual acceptor. Submission requires lawful, consensual adult use.

## Unattended remote operation

Native Firebase authentication requires the dedicated `pti-native-firebase-auth` configuration from `tools/pti-mcp/scripts/configure-native-auth.mjs` (existing cloud CI identity). Pass its local public JSON artifact with `install.ps1 -NativeAuthConfig <path>`; upgrades reuse `.runtime/native-auth.json`. The installer registers both tasks even when the main task already exists. This key allows only Identity Toolkit and Secure Token, with no application restrictions; the browser/Picker key retains its separate restrictions. No native request spoofs a Referer or falls back to the browser key. `device-auth-key-restricted` (HTTP 403) is a configuration incident; `device-login-required` indicates a rejected refresh credential. Neither deletes the DPAPI identity. Check cloud/local active work and inference processes before an idle-only restart. The recovery task uses Windows Script Host to create its PowerShell child hidden and propagate its exit result.

The PC has its own Firebase anonymous identity, separate from the owner's Google login. Its public UID is pinned in `velum-gallery/device-config.mjs` and the security rules by trusted installation. Its refresh token and random 256-bit enrollment grant are stored only in `.runtime/device.dpapi`, encrypted with Windows DPAPI CurrentUser and restricted to that Windows user and SYSTEM. Tokens are never printed, committed, sent to Hosting, or stored as cloud documents. Refresh rotation is saved atomically before the replacement session is used. No monitor credential, browser token, Admin key, Drive permission, public PC port or local browser sign-in is used.

Open Velum Studio on the phone using the PTI owner account and choose **Approve this PC** once. Only the exact pinned device can request this owner-only binding; an unrelated account cannot impersonate it by copying a machine label or grant hash. Pending grants expire after 24 hours and renew automatically; approval does not expire with the grant. Only the owner can revoke or explicitly re-enable the binding. The device cannot approve itself, replace its approved binding or revive a revoked identity. Revocation blocks cloud access immediately and the worker checks during inference at most every 15 seconds, aborting only its own child. Reboots, refreshes and routine network outages require no new owner approval.

Install the pinned worker SDK dependencies with `npm ci --prefix tools/velum-worker --ignore-scripts --no-audit --no-fund`, then run `./tools/velum-worker/install.ps1` once for installation. It registers **PTI Velum Studio Worker**, a dedicated windowless native host with an interactive-user logon trigger and one-minute retry trigger, IgnoreNew, no time limit and a per-user mutex. It also registers **PTI Velum Studio Recovery**, a separate one-minute, current-user helper that can read one fixed owner-only Firestore start request while the main worker is stopped. The helper can only start the fixed Velum Worker task; it cannot execute a command from Firestore. A fresh worker heartbeat, not the helper's acknowledgment, confirms success. `start.ps1` requests the main task locally; it does not start another login session. No unrelated task or service is changed.

Idle queue dispatch uses outbound Firestore listeners under the same pinned anonymous device identity and security rules as REST: its own binding document, then separate device-assigned `queued` and `running` job queries, each limited to twenty records, only while server-confirmed approved. Cached snapshots cannot approve the PC or trigger work. New membership, initial connection and reconnect wake one serialized queue sweep; progress-only snapshots do not. Notifications carry no job bodies into logs or status. The existing REST approval checks, update-time claim preconditions, worker lock and durable no-resample recovery remain authoritative. A server revocation closes the job listeners and aborts only the worker's own active inference child; the separate fifteen-second REST revocation guard remains during inference.

Quiet maintenance runs once per minute for the existing normal heartbeat, binding/grant check, protected session renewal and finite CPU-only thumbnail backfill; it does not query jobs while the listeners are connected. Startup, notifications and reconnects sweep the existing bounded REST queue. A disconnected/unavailable listener permits a queue sweep at most once per minute without a new notification. Terminal listener errors retry with bounded backoff; REST/network/auth failures retain the existing five-second to two-minute backoff and protected identity. The SDK receives only the current ID token: refresh-token rotation still commits through DPAPI before use, and the listener is replaced when that token changes. Local `.runtime/status.json` reports `transport: firestore-listener` and `listenerConnected`; listener availability is separate from owner approval and worker freshness. No GPU model loads while idle.

Source/CI acceptance does not activate this transport in an already-running worker. Dependency installation and a coordinated idle-only worker restart remain a separate activation gate. Do not stop/restart/install/update the worker during another active Velum task, an active inference child or pending saved-output delivery. Live acceptance must verify quiet connected operation and a genuine owner-authorized roundtrip after that gate; deterministic/emulator fixtures do not establish installed or owner-device acceptance.

The owner can open **Studio → PC connection → Request worker start** on another device once the helper has been installed and confirmed as `recoveryControl` by worker v2.2.0. The request expires in ten minutes, is limited to one per minute, and is acknowledged only by the pinned approved PC. The helper itself uses the existing DPAPI-protected anonymous device credential, never asks for local Google sign-in, and does not touch Drive. The helper does not work while Windows is sleeping, shut down, signed out or offline. Wake-on-LAN or an always-on external relay is a separate capability, not silently enabled here.

For a PC that is powered on but not checking in, inspect *both* named tasks before changing the installation: `Get-ScheduledTask -TaskName 'PTI Velum Studio Worker','PTI Velum Studio Recovery'` and `Get-ScheduledTaskInfo -TaskName 'PTI Velum Studio Worker'`. A missing/disabled worker task cannot be fixed by a web-only request; restore the reviewed local installation. Likewise the independent `PTI Local Codex Relay` task controls the separate ChatGPT-to-PC bridge. The Codex desktop window is not that relay.

This non-elevated installation runs while the Windows user is signed in, including a locked screen, and resumes at the next logon. **Powered on but signed out, or rebooted before Windows logon, is not enough.** Pre-logon service startup requires a separate privileged installation and an appropriate protected-secret principal; it is not claimed here. Sleeping, offline or powered-off PCs cannot infer or be woken by the PWA.

The cloud namespace is `users/{ownerUid}/velumStudio/workspace`: `devices/{deviceUid}`, `status/pc`, `jobs/{id}`, immutable `jobs/{id}/chunks/{index}`, owner-only `feedback/{id}` and reversible archive exclusions at `removed/{id}`. Only the owner creates jobs. The approved device can read assigned jobs and publish status/output, never create requests, edit raw prompts/seeds or forge owner feedback. Legacy generic grants reject anonymous accounts and the pinned device UID even after provider linking. A missing rules release fails closed. Claims use Firestore update-time preconditions. Interrupted claims with no valid saved output fail visibly; saved output uploads resume after reconnect/restart without resampling.

## Models and resources

Five models are recognized: Z-Image Turbo NVFP4, FLUX.2 Klein 4B FP8, RealVisXL 5 FP16, Realistic Vision 6 FP16 and Qwen-Image 2.1. The original four engines retain their files and supporting encoders/VAEs under `H:\AI-ImageGen\portrait-pilot\models`. Qwen's separate installed assets and Python environment remain read-only under `H:\AI-ImageGen\velum-qwen21-research-20261103`. Installation detection checks exact byte sizes and the pinned Qwen runtime source/dependency version; it does not perform a fresh full-weight hash audit or load a model. No models, licenses or runtimes are downloaded.

Inference reuses `F:\Workspace\Support\tools\local-image-gen\ComfyUI` and its existing venv. Each job runs offline in a disposable hidden Python process, holds a shared OS inference lock, uses dynamic/offloaded loading, staged Qwen encoding for FLUX/Z-Image and tiled VAE decoding. No inference occurs while idle. Guards require 6 GiB RAM at start, stop below 5 GiB RAM, above 7500 MiB total GPU memory, at 78 C, below 20 GiB H-drive free space, or after thirty minutes. Only the worker's own inference process is interrupted. Sampling failure is never an image-quality verdict.

Qwen v2.3.0 uses `infer-qwen.py` and the existing isolated CUDA 13 environment, with pinned ComfyUI v0.43.0 source at `F:\Workspace\Support\LocalCodexBridge\scratch\qwen21-quality-20261103\ComfyUI` (revision `426f5eea52a7ece1dd599fff4cb6cd1f352ddd24`). It calls native `TextEncodeQwenImage21` and `QwenImage21Cache` and asserts the exact encoder/diffusion families. CPU reference VAE encoding, CPU Qwen3-VL encoding, offloaded diffusion and CPU FP32 VAE decoding run in separate stages. Sampling is Euler/simple, 40 steps, CFG 1, batch one, full denoise and an empty negative prompt. Native CPU reference-cache storage retains default lossless precision. The existing shared `H:\AI-ImageGen\portrait-pilot\velum-studio\inference.lock` serializes both engines. Qwen has a bounded two-hour child guard and a thirty-second parent margin; the other engines keep thirty minutes. All existing RAM/VRAM/thermal/H-disk guards remain, with an additional 10 GiB free-F guard for Qwen. The worker's fifteen-second approval/freshness checks continue during encoding and sampling; no lease expires at thirty minutes.

Qwen outputs, input copies, diagnostics and caches live under `tools/velum-worker/.runtime/qwen21` on F. Its existing H models/venv and F pinned ComfyUI source are never written by inference. Model resources release on disposable process exit. Stage progress reports only encoding-references, encoding-prompt, loading-diffusion, sampling or decoding, with no prompt/media in status. Qwen's installed research license is for noncommercial research/evaluation; this private local adapter does not create a commercial serving endpoint.

Prompts pass unchanged to CLIPTextEncode. SDXL/SD1.5 use an empty negative prompt; FLUX/Z-Image use the architecture's zero conditioning. Seeds, sampler, dimensions and settings are retained in each genuine PNG and job manifest. Outputs/cache/temp stay under `H:\AI-ImageGen\portrait-pilot\velum-studio`; source and runtime status stay on F. Model resources are released by process exit after every job.

## Private results and limits

Full original PNG bytes are transferred through owner-only Firestore chunks (600,000 base64 characters each, at most sixteen, 7.2 MB original maximum). Browser preview verifies size, PNG signature and SHA-256 before displaying a blob URL. Originals and result metadata remain under `H:\AI-ImageGen\portrait-pilot\velum-studio\<job-id>\image.png` and `result.json`; no retention cleanup is performed. This transfer uses Firestore read/write/storage quota. It creates no public download URL and never uploads private media to Hosting/GitHub. Download and Save to Drive are explicit. Feedback records Keep/Iterate/Reject and exact notes; it never changes future prompts automatically.

Creations pages 36 metadata records at a time and lazily fetches SHA-verified JPEG thumbnails (512px edge, at most 64 KiB), with six concurrent thumbnail reads. Full originals load only for selection. Idle CPU-only thumbnail backfill walks device-assigned jobs in 24-record cursor pages and processes one existing H original per pass. Missing local files and legacy jobs without this device assignment retain a truthful thumbnail placeholder; no remote PNG backfill or inference is triggered. Existing chunks, feedback and originals are preserved.

Reference jobs use schema 3: up to two PNG/JPEG images for FLUX.2 Klein 4B FP8 native reference latents, or one image for Z-Image Turbo, RealVisXL 5 and Realistic Vision 6 through VAE image-to-image (denoise 0.62); inputs, each normalized by the phone to at most 1024px/2 MiB, transported privately under the job. Client and worker validate signatures, dimensions, byte counts and SHA-256; bounded Pillow decoding fails before inference. Owner uploads are immutable and inference cannot claim an incomplete upload. The owner can abandon an incomplete transfer without deleting bytes. Native `ReferenceLatent` conditioning follows the official ComfyUI Klein edit workflow; each reference is VAE-encoded at a 0.25-megapixel conditioning limit. Output is 512x768, as verified with two synthetic references on this RTX 4060. There is no mask, pose-control or face-identity guarantee. Source provenance, parent job and the unchanged instruction are retained with each new output. Input download can retry; a persisted inference-start marker prevents restart from silently resampling.

Schema 4 adds Qwen (zero text-only references or one through ten distinct image references) and an explicit prompt/pose contract for any supported engine. Other engine reference caps remain two/one. The ten-reference Qwen total includes the optional pose image; no source is silently dropped, duplicated, collapsed into a contact sheet or treated as metadata-only. Duplicate SHA-256 values and repeated nonempty Drive IDs are rejected. Existing per-image limits remain 2 MiB, 1024px edge, 1,048,576 pixels and five chunks of at most 600,000 base64 characters. Qwen reference aspect ratios must be between 1:8 and 8:1. Each schema-4 input has an immutable ready manifest `{index,sha256,bytes,chunks}` under `jobs/{id}/inputs/{index}`, published only after its immutable chunks exist. Queue promotion checks the bounded manifests; the worker verifies each manifest and rehashes/decodes the actual bytes before inference.

Qwen passes every accepted image to a separate native image slot. Its native node normalizes each reference to approximately 1024 squared pixels and uses the first reference's aspect ratio for the output canvas, rounded to multiples of 32. `jobDimensions` derives that exact canvas; the worker verifies it against the native latent. A pose image is appended after the subject so it cannot silently become the canvas. Text-only output remains 768x1024. No reference is reshaped to the legacy 512x768 canvas for Qwen.

Schema 4 stores original `prompt` unchanged (at most 6,000 characters), `effectivePrompt` (at most 8,000) and optional `pose` with exact catalog/file/category/label/instruction provenance, mode and reference index. Without pose, effectivePrompt must equal prompt. With pose it must equal `prompt + '\n\n' + pose.instruction`; this is the exact string passed to the native encoder. Image mode binds the pose's Drive file ID to one actual reference with role `pose`; honestly labeled text mode uses index -1 and no pose image. PNG and result metadata retain original/effective prompts, references, parent, pose and actual settings. Saved-output recovery verifies those fields before publication. Schemas 2/3 retain their previous contracts and cannot smuggle schema-4 prompt/role fields.

Save to Drive runs entirely in the owner's browser using incremental `drive.file` consent and Google Picker approval of the existing pinned Private folder. Originals are resumably uploaded into that exact folder root. An immutable owner-only upload reservation keeps one preallocated Drive file ID across browsers/retries. A save receipt is written only after verifying the resulting Drive object's job/hash/size/parent. OAuth tokens and upload session URLs never enter cloud documents or the worker. Actual consent, Picker configuration and a completed upload require phone-side acceptance; tests do not substitute for that grant.

The existing Firebase CI identity checks Service Usage activation, archive indexes and the public web key's Picker restrictions. A Drive endpoint's expected `401 CREDENTIALS_MISSING` is distinct from `SERVICE_DISABLED`; it is not an enablement failure. Completed/no-op service operations are accepted immediately, while permission errors and unfinished operations remain explicit. No Admin credential is placed on the PC for this setup.

Owner requests can queue while an approved PC is offline and expire after seven days. Studio distinguishes approval, verified installation, a fresh worker heartbeat, connectivity, active work and errors. The PC panel also shows last contact, a bounded recovery request's state and whether the helper is installed. Installation hints survive a stale heartbeat; an offline PC or an acknowledged-but-unconfirmed recovery is never presented as online. Work begins automatically when the Windows session is awake and online again.

## Checks

`npm test --prefix tools/velum-worker` tests raw text, byte transport, device/project/provider binding, persisted sign-in, real Windows DPAPI, interrupted/reconnected output delivery and no-resample recovery, plus retained/coalesced event wakeups, quiet connected queue suppression, bounded offline sweeps, token replacement, stale callback disposal and listener revocation. Rules tests cover owner/device isolation, immutable prompts, pending-grant expiry, revoke/re-enable, offline queue expiry and legacy denial. `queue-events.rules.test.mjs` uses synthetic emulator jobs to verify the actual bounded listener queries, owner queue wakeup, cross-device exclusion and revoke/re-enable behavior. They run through the existing One Piece emulator and Firebase workflow. `smoke.mjs` remains an explicit engine test; the existing successful bounded FLUX smoke is reused as evidence, not rerun for UI QA.

`qwen.test.mjs`, gallery `studio-contract.test.mjs` and CPU-only `python -B -m unittest qwen_test media_test` cover engine isolation, bounded timeouts, native canvas calculation, model-family refusal, 0/1/10/11 reference boundaries, exact prompt/pose lineage, manifests and complete native input forwarding. Conditioning fixtures are labeled synthetic; they do not establish ten-image VRAM/latency or output quality. Current source acceptance does not activate an already-running worker or establish a genuine Qwen Studio roundtrip. Parent-owned idle-only activation and bounded actual inference acceptance remain required.

End-to-end acceptance requires the one-time **remote Velum owner approval**, an actual Studio submission, genuine returned image and saved owner feedback. Local interactive sign-in is not part of this architecture. A genuine two-reference synthetic engine smoke succeeded at 512x768 in 215.73 seconds, SHA-256 `470de62db13363ff9847a5f520ebf5a70215d0df09cde5f3a67aed95cbc24c84`; its private H output was not uploaded. This establishes native conditioning and resource cleanup, not the authenticated phone-to-PC roundtrip or owner visual acceptance.
