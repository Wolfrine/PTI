# Velum Auto Review

Auto Review lives in Velum Studio. The owner approves a text editing seed, up to six exact unshared image versions from Private/References, and the configured image model. They confirm permission and non-intimate scope with every revision of those settings. The prompt-construction guidance has its own editor, approval and version. It controls phrasing and leaves the editing seed intact. Qwen-Image 2.1 Turbo is the default. The selected model must be advertised by the approved, recently seen PC.

## Run and review

- The owner starts a batch of one to three edits, within the remaining approved admission limit. Auto Review rotates through the approved source pool, verifies folder lineage, current permissions and exact approved versions, and selects distinct eligible images. It skips missing or changed versions. Each run, Studio job, and admission increment are created together. Each job stores its seed revision, independent prompt-guidance revision, Drive version, normalized reference hash and numeric sampling seed. Source originals remain in Drive.
- Vision Model 1, local Qwen3-VL 2B Instruct, reads the verified reference and approved seed and proposes one concise edit prompt. A refusal or invalid response stops that run before image inference. The worker seals the derived prompt before sampling and executes it through the existing configured image model. Normal Studio jobs retain their existing prompt path.
- Vision Model 2, local Qwen3-VL 4B Instruct, compares the verified normalized reference and exact PNG against the approved seed and actual edit prompt. It records an observation before review. A failed comparison retries at most once against the existing PNG, without sampling again. The owner can review the staged image if this comparison is unavailable.
- Start reserves the exact run IDs and their private staging folder under the existing Google connection. Once sources are queued, Studio can close or lock. The PC processes the queue serially and submits each ready run ID with its existing pinned Firebase device identity. The Function keeps the owner grant server-side, rechecks approval and Drive lineage, and uploads only the hash-verified PNG to the reserved file ID in unshared Private/Review staging. It confirms the private parent, size and content hash. Folder authorization through the existing Picker is required once if the connected app lacks the folder grant. Each item has at most two automatic staging attempts. If confirmation fails, the owner can reconcile the same reserved file in unlocked Studio.
- The queue retains every admitted item. Pause holds edits that are waiting to start. Resume releases them. Stop cancels waiting or incomplete transfers. An edit claimed before the cutoff can stage for up to one hour from its claim while the Drive grant and device approval remain valid. Existing staged results remain available for review.
- The comparison shows the staged edit and the exact normalized reference supplied to the model. Holding peeks at the reference, and tapping or keyboard activation toggles the comparison. Acceptance records the owner's intent before moving the same PNG directly into the existing Private folder. The browser verifies the parent and hash before recording acceptance. The existing gallery Sync discovers the accepted image for Drift and Browse. The staging folder and its contents fall outside that discovery.
- Not Okay keeps the PNG in staging. Saving the decision queues one local Vision Model 2 follow-up with the exact original, exact output, actual edit prompt and owner feedback. The result proposes an editable Vision Model 1 guidance revision. Applying it requires explicit owner approval, and the editing seed has its own approval. The owner can edit, save, and approve learning from either outcome. Prior runs keep their original approved revisions.

## Release and usage

Release the existing `velumDrive` Function, the exact main revision to Velum Hosting, and the reviewed Velum rules through the existing release lane. The owner-administered `autoReviewControl/activation` document takes integer fields `until` (UTC epoch milliseconds for admission) and `maxRuns` (cumulative admissions, including closed runs). Keep activation closed until usage and the owner-approved cap and expiry are recorded. New reservations expire at the earlier of the admission cutoff and 24 hours. Setting `until` to zero blocks fresh reservations, queue promotion and claims. Use Stop to cancel already reserved waiting items. Staged receipts remain reviewable after admission closes.

The app reuses the existing worker, Function, private grant, Firestore and visible-session status stream. There are no scheduled jobs or paid model calls. Each admitted run can add up to 2 MiB of reference bytes, 7.2 MB of result bytes before base64 and Firestore overhead, and one Drive PNG of up to 7.2 MB.

The 26 November review measured the existing Function at 1 vCPU, 256 MiB, request-based billing, a 60-second timeout, and a revision maximum of two instances. Firestore is Standard in Mumbai and the Function runs in Iowa. At list prices the estimates are US$0.003–$0.05 once for the scoped release, or $0.21 for a longer build, and $0.04–$0.15 gross in a normal month including conservative artifact retention. Ten illustrative high-usage runs total up to $0.39 gross including retention. These scenarios assume 32–64 MiB aggregate transfer, 500–2,000 reads and writes each, and 15 MiB of retained Firestore data per run. They assume no credits or shared free allowance. Live daily usage, eligible credit coverage, Drive headroom and an approved production run cap and expiry remain open. See [Cloud Run](https://cloud.google.com/run/pricing), [Firestore](https://cloud.google.com/firestore/pricing), [Cloud Build](https://cloud.google.com/build/pricing), [Artifact Registry](https://cloud.google.com/artifact-registry/pricing) and [Drive quotas](https://developers.google.com/workspace/drive/api/guides/quotas).

The worker uses the official pinned checkpoints and local llama.cpp archives in the [model manifest](../../tools/velum-worker/review-vision-models.json). Install under the declared H-drive root after SHA-256 verification. Vision uses one authenticated loopback process at a time, a 180-second watchdog, one shared inference lock, four CPU threads and one GPU workload. A Windows job object tears down the child, including on parent interruption. Batches require protocol 3. After the Function, Hosting and rules releases are verified, set `review-v3.enabled` in the vision runtime root to `review-v3` and restart the existing worker while idle. Verify its fresh status advertises protocol 3 before opening admission. For rollback, close admission and drain existing claims before removing the protocol marker and restarting.

## Design and verification

The dialog extends the existing Studio visual direction. The image and hold gesture lead the review, with the decision and owner seed adjacent on desktop and stacked on mobile. The key checks are immediate comparison without layout jumps, legible controls at phone width, and clear distinctions between working, staged, resolving acceptance, accepted, and rejected. Configuration and history use disclosures. Central release 0.2.3 guided the bounded Studio extension.

Independent source review covered the owner scope, local inference, Drive lineage, rules and comparison recovery. A private production run requires owner authentication, approval of an exact source pool and seed, and a bounded production admission. Worker startup and local model readiness are recorded separately from image quality and review acceptance.
